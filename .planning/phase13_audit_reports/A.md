## Findings

- **HIGH** — Frontend defensive parser `_parseRefusedClaims` at `advisorCritiqueClient.ts:167-176` validates ONLY the marker prefix (`startsWith(REFUSED_CLAIM_MARKER_PREFIX)`), NOT the close-set membership of the suffix against `ADVISOR_FORBIDDEN_TOKENS`. A tampered backend response (MITM / proxy injection) could deliver `refused_claims: ["refused: production ready for service deployment"]` and the parser would accept it, AND `_RefusedClaimsSection` (`AdvisorPanel.tsx:258`) would render the marker text VERBATIM without running it through `isAdvisorEntrySafe`. The four content sections DO route through `isAdvisorEntrySafe` at line 340, so the unsafe content cannot reach those sections. But the suppression-history surface is a defense-in-depth gap — the verbatim marker text reaches the rendered DOM. **Impact bounded**: the backend `_filter_section` only ever appends `f"{REFUSED_CLAIM_MARKER_PREFIX}{token}"` for `token in ADVISOR_FORBIDDEN_TOKENS` (closed set), so a non-tampered path is safe. The threat model is JSON tampering on the wire between backend and frontend. **Suggested fix**: extend `_parseRefusedClaims` to require `(ADVISOR_FORBIDDEN_TOKENS as readonly string[]).includes(item.slice(REFUSED_CLAIM_MARKER_PREFIX.length))` — close-set-validate the suffix. Add a vitest case `"discards markers with arbitrary text suffix not in ADVISOR_FORBIDDEN_TOKENS"` to pin the new behavior. This is a HIGH finding because the methodology doc (line 38) explicitly claims "Does NOT echo original content. The marker names WHICH token tripped the audit, not WHAT context the LLM tried to assert" — but the frontend parser does NOT enforce that contract for tampered payloads. The backend honors it; the frontend has a hole. Slice B is the right place to close this since the surface is a frontend client + panel.

- **MEDIUM** — `test_audit_first_token_wins_when_multiple_forbidden_tokens_present` (`test_phase13_refused_claims.py:156-174`) admits EITHER `"validated against"` OR `"production ready"` as the first-encountered marker, but the methodology doc (line 39) explicitly names "ADVISOR_FORBIDDEN_TOKENS declaration order" as the contract. The implementation iterates tokens in tuple order (advisor_critique.py:590) so `"validated against"` (the first tuple entry that matches a substring in the test input) is the deterministic winner. A future refactor that iterates tokens differently (e.g., sorts them) would silently break the methodology-doc contract without tripping this test. Suggested fix: tighten the assertion to `marker == f"{REFUSED_CLAIM_MARKER_PREFIX}validated against"` exactly. Not a slice-A blocker because the underlying iteration order is correct, but a regression-protection gap.

- **LOW** — `_RefusedClaimsSection` (`AdvisorPanel.tsx:258`) renders marker text verbatim without applying `isAdvisorEntrySafe`. As noted under the HIGH finding, this is fine for backend-produced markers (closed-token set) but is a defense-in-depth gap for tampered payloads. Even if the parser is tightened per the HIGH suggestion, applying `isAdvisorEntrySafe` to rendered markers AS WELL would be a belt-and-suspenders X:-2 guard. The current implementation passes `isAdvisorEntrySafe(marker)` accidentally (markers have `"refused: "` prefix and the forbidden token is preceded by `": "` which doesn't end with `"not "` — so a marker like `"refused: production ready"` would FAIL `isAdvisorEntrySafe` because `"production ready"` is found outside disclaimer form). Adding the `isAdvisorEntrySafe` filter would surface a contradiction (the very markers we want to render would be refused). The right fix is per the HIGH: close-set-validate the suffix in the parser, and accept that markers are SAFE by construction.

- **LOW** — The methodology doc references a future retrospective at `.planning/retrospectives/fm04a_phase13_carry_forward_closure.md` (TBD)` on line 96, but no such file is created in this slice. A future slice (G or similar retrospective) should land it. Not load-bearing for slice A.
