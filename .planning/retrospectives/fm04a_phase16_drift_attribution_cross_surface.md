## What worked

1. **Schema-MINOR-bump composability**. Three independent envelopes (`TrustScoreTimeline` + `cohort-anomalies` + `SignoffRecord`) each accepted one additive optional field with a MINOR bump and a bump-history docstring. The Phase 15 C SSOT helper `compute_drift_attribution` is the shared compute primitive; the per-consumer wrapper code is <30 LOC each (timeline uses `compute_drift_attribution(_axes_dict(points[0]), _axes_dict(points[-1]), ...)`; signoff calls `build_trust_score_timeline(case_id, repo_root).inter_snapshot_drift_attribution[-1]`; cohort-anomalies has its own thin wrapper that iterates per-case via the SSOT helper). The anti-gaming M:-2 guard (consumer IMPORTS the helper, no inline percentage math) lands cleanly across all 3 slices.
2. **A:-3 server-computed pin closes a real attack surface**. The signoff POST surface is the obvious place a client could try to forge a drift attribution (`{"verdict": "needs_more_evidence", "drift_attribution_at_signoff_time": {"dominant_axis": "energy_audit", "dominant_delta_pct": -100.0, ...}}`) to fabricate evidence of regression at signoff time. Slice C closes this by construction: `write_signoff_record` signature does NOT accept the kwarg, AND the helper is server-side, AND `inspect.signature` pins the parameter absence so a future maintainer who adds the kwarg trips the test. Journey 1 step 4 also pins the POST request body has NO drift_attribution_at_signoff_time field (`"drift_attribution_at_signoff_time" not in SIGNOFF_BODY`) so the GET response's drift field can ONLY come from the server. Three independent layers (signature absence + helper server-side + journey-level body audit) for one anti-gaming surface — defense in depth.
3. **SSOT test utility pattern simplifies cross-phase audit discipline**. The 8/9 forbidden tuple split (8-tuple for envelope-rendering audits + 9-tuple for source-file grep, differing only by `certified`) had been silently duplicated across 5 test files before slice D. Hoisting to `tests/_test_utils` with the SSOT helpers + a meta-test fingerprinting future inline duplication closes the Phase 15 retro §7 + §8 carry-forwards in <200 LOC of net code change. The meta-test's lexical detection (FINGERPRINT >= 5 of 9 token tuple-shape entries) is precise enough to NOT flag ad-hoc inline 3-assert blocks (which Phase 16 retro acknowledges as acceptable) while reliably catching the SSOT-tuple-shape duplication. The `check_impact=False` knob accommodates the Phase 15 D Journey 2 PV rubric path (claim_impact legitimately absent) without forcing it to use a separate helper.
4. **Cumulative-vs-per-pair invariant pinned on two arc shapes**. Phase 16 A introduced cumulative as a single-DriftAttribution view; Phase 16 D Journey 2 pins the load-bearing invariant: a stuck regression arc has cumulative-matches-worst-per-pair (because the regression sticks); a recovery arc has cumulative=None-but-per-pair=non-trivial (because the regression recovers). Without Journey 2, a future maintainer could silently break the cumulative-vs-per-pair distinction (e.g., by changing cumulative to span snap-1 → snap-(N-1) instead of snap-1 → snap-N) and only the Phase 16 A unit tests would trip. Journey 2 catches the same regression at the user-visible envelope level, which is the actual UX contract.
5. **Per-verb signed-registry refusal exercised on POST**. Phase 14 A established the cross-route signed-registry refusal SSOT (`assert_not_signed_registry`); Phase 16 D Journey 1 re-exercises it on POST signoff-history (in addition to GET) via `pytest.mark.parametrize` over `(verb, url_template)` tuples. A future regression that drops the POST-verb refusal trips this. The defense-in-depth pattern (Phase 14 A service-layer raise + Phase 16 route-layer 422 + Phase 16 D journey-level pin) holds across all 3 layers.
6. **Existing Phase 12 F / 14 A / 15 D journey patterns transferred without modification**. Both Phase 16 D journeys use the same sync-ASGI-client wrapper + module-scope `journey_repo` fixture + function-scope `patched_routes` fixture as Phase 15 D. The route-count contract test + the per-route signed-registry 422-refusal `parametrize` + the SSOT-helper-based forbidden-token grep all carry across. Phase 16 D added ZERO new fixture-helper patterns; the architectural pieces from Phase 15 D were sufficient.

## What did not work / surprised us

1. **Arc-shape choice for Journey 1 differs from Phase 15 D Journey 2**. Phase 15 D Journey 2 placed the leak-case regression on the snap-1 → snap-2 transition (canonical Phase 15 A state at snap-2 has `energy_audit=open_residual` already). Phase 16 D Journey 1 needs the LATEST pair (snap-2 → snap-3) to be the dramatic one because `cohort_drift_attribution` uses the latest pair AND `drift_attribution_at_signoff_time` is pinned to the latest pair. Initial seeding reused Phase 15 D's pattern and Journey 1 step 1 failed because cohort_drift surfaced `completeness` (the artifact-drop axis from snap-2 → snap-3) instead of `energy_audit`. Fix: use the CLEAN leak variant at BOTH snap-1 and snap-2 (energy 15), so the dramatic snap-2 → snap-3 transition carries the energy collapse (15 → 0). The Journey 1 docstring documents the arc-shape choice + the contrast vs Journey 2 explicitly. **Lesson**: when designing a journey that pins on the LATEST snapshot pair (cohort_drift_attribution / drift_attribution_at_signoff_time), the arc shape must place the dramatic transition on the latest pair; the Phase 15 D Journey 2 shape places it on snap-1 → snap-2 which is correct for that journey's per-pair audit but wrong for Phase 16 D Journey 1's latest-pair audit.
2. **Signoff verdict whitelist tripped first-pass on `hold_for_followup`**. Initial Journey 1 step 4 used `verdict="hold_for_followup"` and got 422: the whitelist is `('watching', 'needs_more_evidence', 'needs_more_convergence', 'blocked_pending_input')`. Fix: switch to `needs_more_evidence`. **Lesson**: read the Phase 9 SUPPORTED_SIGNOFF_VERDICTS whitelist before writing a POST journey; the verdict tokens are NOT free-form. The whitelist itself is the Phase 9 anti-gaming guard C:-10 (load-bearing refusal at request-validation boundary). The fix was trivial; the lesson is that the journey writer must thread the existing service-layer constraints, NOT invent reviewer language.
3. **Meta-test had to be tightened to NOT flag ad-hoc inline 3-assert blocks**. First-pass meta-test used "all 3 trio sentinels present" as the offender shape; this flagged 6 Phase 15+ test files that legitimately carry the 3 trio strings in ad-hoc assertions inside individual test functions (NOT in a duplicated helper). The Phase 15 retro §8 intent is "hoist the HELPER FUNCTION", not "ban all assertions about the trio fields". Fix: shift the detection to LEXICAL HELPER-DEFINITION pattern (`def _assert_tier1_trio(` / `def assert_tier1_trio(`) NOT immediately delegating to SSOT (no `from tests._test_utils` + no `assert_tier1_trio(` call). Forbidden-token tuple detection shifted to FINGERPRINT shape (>= 5 of 9 tokens in tuple-form with trailing comma). The refined meta-test correctly identifies SSOT-helper duplication (the actual violation) while leaving ad-hoc inline assertions alone. **Lesson**: SSOT consolidation enforcement should target the SHAPE-OF-THE-VIOLATION (a copy-pasted helper body), not the SHAPE-OF-THE-USAGE (any assertion mentioning the SSOT tokens).
4. **Ruff reformatted on commit**. As in Phase 15, the pre-commit hook reformatted the 3 slice-D test files after the first commit attempt; re-stage + re-commit succeeded. Mechanical; no logic change. **Lesson**: standard Ruff-on-commit dance; no action item.
