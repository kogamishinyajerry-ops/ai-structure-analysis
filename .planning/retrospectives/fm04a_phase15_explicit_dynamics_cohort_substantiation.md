## What worked

1. **Audit-computed A:-3 invariants compose across slices**. Slice A's leak-case test re-runs `energy_partition_audit` on the parsed manifest to compute the flagged frame index (NOT trusting the fixture's self-reported field). Slice B's bucket-transition test walks the LIVE `build_trust_score_timeline` route to compute trust per snapshot (NOT trusting a hand-rolled snapshot manifest). Slice C's boundary tests reproduce exact percentages by re-deriving from axis weights. Slice D's journey 1 step 2 pins `dominant_delta_pct == -100.0` exactly — re-deriving from the energy axis weight (15 pt) and the 15→0 weighted-point delta. The A:-3 chain — "compute it, don't trust it" — extends across all 4 slices and gives every TAA's adversarial probe a load-bearing pin to target.
2. **Strict-exceed floor semantic landed cleanly at write-time**. Slice C's initial implementation used `< floor` (>=, dominant) which contradicted the test's intended "at-floor not dominant" semantic. The fix — switching to `<= floor` (strictly exceed to count) — was a 1-character source change + 1 methodology-doc line edit + 1 test rerun. Catching this at slice-C boundary (BEFORE downstream consumers wire the floor into UI thresholds) is exactly the "make the constant prominent + test the boundary" anti-gaming guard M:-3 paying off. Future reviewers can read the source + methodology and trust the literal `<=` operator semantic; the C:-8 forbidden-token grep + Tier 1 trio audit ensure no aspirational language slips into either the source docstring or the methodology rationale.
3. **MINOR schema bumps with bump-history docstrings + import-not-inline pattern**. Slice C bumps both alerts (1.0.0 → 1.1.0) and timeline (1.0.0 → 1.1.0) with docstrings that cite Phase 15 C + the additive `drift_attribution` field. The builders IMPORT `compute_drift_attribution` from the SSOT module rather than inline-declaring percentage math; this trips the anti-gaming guard M:-2 (no two-places-of-truth). A future floor bump (e.g., 5.0 → 6.0) requires the SSOT change AND the methodology bump-history entry AND a test boundary update — the gradient is FORCING-the-bump-policy correctly across all 3 surfaces.
4. **Cohort SSOT named-tuple pattern lets Journey 2 lift to 5 cases without route duplication**. Journey 2's `COHORT_CASES = (...)` tuple lists 5 (case_id, analysis_type) pairs as the SSOT; the derived `EXPLICIT_DYNAMICS_CASES` + `LINEAR_STATIC_PV_CASES` filters from the SSOT. A future contributor adding a 6th case updates the SSOT once; the cohort-count contract test, the per-axis flatness/evolution test, and the route-count audit all adapt. The COHORT_MIN_SIZE_FOR_ANOMALY=3 floor is asserted at module-import time so a future cohort shrink below 3 trips at-import (well before the test runs).
5. **Phase 12 F journey pattern transfers cleanly**. Both Phase 15 D journey tests use the same sync-ASGI-client wrapper + module-scope `journey_repo` fixture (subprocess-driven generators + golden_samples copytree + 3 write_cohort_snapshot calls) + function-scope `patched_routes` fixture (monkeypatch each route's `_repo_root` to tmp_path). The journey style — narrative test docstrings naming each route + an explicit `routes_crossed` set + a separate route-count contract test — makes the 6-route binding number auditable without parsing the narrative. The cross-route signed-registry refusal SSOT (Phase 14 A) re-exercised via `pytest.mark.parametrize` over 5 routes gives a clean A:-3 pin in <10 lines per journey.

## What did not work / surprised us

1. **Slice C floor semantic ambiguity caught at first test run**. The initial implementation read `if max_abs < dominant_floor_pct: dominant_axis = None` which means 5.0% exact → NOT discarded → would-be-dominant. The test asserted the opposite (5.0% exact → None). Methodology doc said "< 5.0% is NOT counted as dominant" which is the implementation's semantic (not the test's). The fix was straightforward but the methodology language was self-consistently wrong with the test. **Lesson**: when introducing a floor-style constant, the implementation + test + methodology MUST agree on the boundary operator (`<` vs `<=` vs `>` vs `>=`) in the same change. The cleanest fix here was making the implementation `<=` (strictly exceed to count) and updating the methodology + module docstring to say "strictly exceed". Pinned by a dedicated test `test_at_floor_exact_does_not_count_as_dominant`.
2. **Forbidden-token grep needed `no <claim>` allowance for module docstrings**. The Phase 15 C module docstring lists forbidden tokens in the "Forbidden wording" header using the form ``no ``perforation completed``,``. The initial test grep only allowed `not <claim>` prefix and tripped on the source-code docstring (the literal forbidden-token list itself). Fix: extend the allowed-prefix audit to accept both `not` and `no` after stripping backticks/quotes. **Lesson**: the docstring "Forbidden wording" header is a CITATION of forbidden tokens, not a USE; the grep MUST tolerate that pattern, or every module that documents its own constraints fails the audit. Phase 14's existing `_assert_no_overclaim` grep runs on RENDERED REPORTS at request time, not source code at import time, which side-stepped this entirely; Phase 15 C's source-code grep is stricter and needed the additional prefix allowance.
3. **`cohort-overview` route does not carry `regressed_count`**. The Phase 15 blueprint §3.D Step 1 names ``GET /api/v1/cohort-overview/{snap-3-label}`` as the surface for the regressed-bucket observation. In reality `cohort-overview` carries the COMPLETENESS-score distribution (`completeness_distribution["0-49"]` / `["50-79"]` / `["80-99"]` / `["100"]`); the TRUST-score buckets (`healthy_count` / `watching_count` / `regressed_count`) live on `cohort-executive-summary`. The blueprint also stipulated a URL shape (`/{snap-3-label}`) that doesn't exist — `cohort-executive-summary` is a non-parameterized GET. Journey 1 uses `cohort-executive-summary` and the test docstring explicitly documents the deviation + the engineering-deliverable preservation. **Lesson**: blueprint route names are aspirational sketches; verify against the actual route surface before writing the journey. The discrepancy is documented for any future audit reading the blueprint side-by-side with the test code.
4. **Snap-3 trust dropped only to 52 on first try; needed to omit 3 optional artifacts (not just 1) to land below 50**. Slice B's first attempt dropped only the generator_script_path for snap-3 regressed leak case; the leak case landed at trust = 52, which is in the watching bucket (50 ≤ trust < 80), not regressed. The test failed because the cohort `regressed_count` was 0. Fix: omit animation_manifest_path + notes_path + generator_script_path together; trust drops to ~47. **Lesson**: the regressed-bucket trigger needs MULTIPLE optional-artifact drops on top of the energy-axis failure; a single-artifact omission doesn't move the trust score far enough below 50. The Phase 13 C `cylinder-pv-collapsed-candidate` precedent (also needed multiple drops) gave the design pattern but the per-case numerics needed verification.
